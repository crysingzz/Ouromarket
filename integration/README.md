# Настоящий Ouroboros в Ouromarket

Исходники в `../ouroboros-runtime/` — Git submodule с upstream-коммитом из [upstream.json](upstream.json). Версия 6.114.0 закреплена, её файлы не изменены. Старый рабочий checkout с пользовательскими изменениями не перемещается и не публикуется. Рабочей структурой платформы является checkout с тремя соседними каталогами `adaptive-alpha`, `ouroboros-runtime` и `integration`.

## Запуск и проверка

Из корня платформы:

```sh
git submodule update --init ouroboros-runtime
python3 integration/bootstrap.py
docker compose -f integration/compose.yaml up --build -d --wait
uv --project adaptive-alpha run python integration/smoke.py
```

Для Git submodule не используется `update --remote`: версия меняется только явным обновлением закреплённого коммита и повторной приёмкой. Bootstrap проверяет HEAD и отсутствие изменений, затем создаёт сервисный токен в `integration/.secrets/ouroboros_token`, не выводя его. Каталог имеет права 0700, файл 0444 для чтения non-root пользователем контейнера через secret mount. Токен отличается от операторского токена Adaptive Alpha и от OpenAI API-ключа.

`http://localhost:8765/api/health` отвечает настоящим upstream healthcheck. Остальные разрешённые маршруты требуют `Authorization: Bearer <сервисный токен>`; даже запрос с loopback не обходит наш gateway. Этот порт предоставляет API интеграции, а не общий интерфейс администрирования Ouroboros. Основной UI платформы остаётся на `http://localhost:8787`.

Текущий профиль `protocol-bootstrap` работает без модели и API-ключей. `/integration/status` возвращает `ready=false`, `execution_enabled=false`. `/api/tasks` доходит до настоящего upstream-обработчика и возвращает 503 `worker_pool_unavailable`, пока нет исполнителей. Это ожидаемый результат проверки, не успешно выполненная задача. Проверка фиксирует отказ, авторизацию, независимые Git-workspace и недоступность настроек/защищённых путей в `.state/protocol-acceptance.json`.

## Связь с Adaptive Alpha

После подготовки базового приложения и запуска runtime:

```sh
docker compose --env-file adaptive-alpha/.env \
  -f adaptive-alpha/compose.yaml -f integration/alpha.override.yaml up --build -d
```

Override добавляет research-worker и отдельный engineering-worker в закрытую сеть инженера; сервисный токен получает только этот контур. Research-worker фиксирует спецификацию и ждёт устойчивую очередь, engineering-worker арендует WorkOrder и обращается к runtime. Он включает серверное создание workspace. API, оценщик и брокер не получают Docker socket или исходники Ouroboros. При иной структуре checkout можно явно задать абсолютный `ALPHA_ENGINEERING_TOKEN_FILE`. Относительные пути Compose разрешаются относительно первого файла `adaptive-alpha/compose.yaml`.

Для каждого WorkOrder создаётся Git-репозиторий `/workspaces/work-<uuid>` с зафиксированным `work-order.json`; он не пересекается с `/opt/ouroboros` или `/state/data`. Повтор требует совпадения манифеста и хеша спецификации. Подмена пути, symlink, изменение манифеста или недопустимый тип задачи отклоняются. Рабочие директории сохраняются на отдельном volume для диагностики; автоматического удаления сейчас нет. Это разделение заданий внутри одного доверенного сервиса, ещё не полноценная изоляция произвольного кода между арендаторами.

Адаптер проверяет готовность инженера **до** обращения к исследовательской модели. При текущем bootstrap-профиле обычная кампания завершится ошибкой готовности и не потратит токены исследователя. Отсутствующая модель не подменяется генератором-шаблоном.

## Образ и права

Образ собирается из submodule на Python 3.12, используя собственные upstream `uv.lock` и uv 0.12.1. Окружение Adaptive Alpha остаётся отдельным. Начальный headless-профиль не устанавливает необязательные браузерные зависимости. В образе создаётся Git-снимок скопированных исходников: его служебный commit отличается от upstream commit, который отдельно записан в manifest и image label. Исходный Git submodule, а не этот служебный commit, задаёт версию поставки.

Runtime запускается non-root, с read-only корнем, без capabilities, с ограничением CPU/памяти/процессов. Ему доступны только собственные state/workspace volumes и сервисный токен. Его сеть internal, без выхода наружу. Входящий прокси публикует только localhost и не получает секретов или volume с данными. Эти ограничения принимают текущий протокол; промышленная безопасность исполнения генерируемого Python требует отдельной проверки gVisor.

## Следующий этап

Нужно подготовить исполняющий профиль с проверенным runsc, выбранной моделью OpenAI, отдельной передачей ключа, лимитами модельных вызовов и наследованием бюджета субагентами. Ключ нельзя записывать в исходники, Dockerfile или сообщения; официальная [документация аутентификации OpenAI](https://developers.openai.com/api/reference/overview) описывает серверную передачу ключа. Наличие ключа в настройках исследователя не означает его автоматическую передачу инженеру.

Затем принимается реальный WorkOrder → модель Ouroboros → версия стратегии/skills/subagents/harness → runner → лаборатория, с устойчивыми попытками, аудитом, отменой и UI. Операторский допуск повторно используемых инструментов и измерение инженерного саморазвития следуют после этой приёмки. Учёт модельных токенов и создание артефактов пока не проверены реальным запуском.
