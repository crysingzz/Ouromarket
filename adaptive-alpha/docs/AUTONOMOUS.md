# Автономный исследовательский контур

Дополнения v0.3 описаны в [LIFECYCLE.md](LIFECYCLE.md). Режим Ouroboros теперь сначала вызывает отдельного исследователя OpenAI для неизменяемой ResearchSpec, затем передаёт инженеру только её реализацию. Поэтому ему также нужен ключ OpenAI. Новые скиллы/субагенты/harness сохраняются как предложения для рецензирования; их произвольное исполнение не включено. Инструкции ниже описывают исходный прямой режим OpenAI v0.2.

## Настройка без терминала

1. Откройте `http://localhost:8787/#autonomous` и раздел **Autonomous R&D**.
2. Нажмите **Настроить OpenAI**. На странице [OpenAI API keys](https://platform.openai.com/api-keys) создайте ключ, вставьте его в поле приложения и нажмите **Проверить и сохранить**.
3. Выберите модель из списка доступных вашему ключу и сохраните ещё раз. Проверка получает список моделей; исследование запускается отдельно.
4. Нажмите **Создать тестовые данные** для проверки механики. Для содержательного исследования импортируйте рыночный JSON с происхождением данных.
5. Задайте цель, поисковый запрос и бюджет, затем запустите кампанию. Статус и артефакты обновляются автоматически. Для трёх поколений удобно задать общий лимит 90 000 токенов.

Ключ хранится локально в Docker volume `provider-vault`. Не помещайте его в чат или git. Альтернатива — файл `.secrets/openai_api_key`, читаемый только контейнером worker. Настройка через UI имеет приоритет над этим файлом. Модель должна поддерживать Responses API и Structured Outputs; наличие в списке аккаунта само по себе этого не гарантирует.

## Что выполняется

Campaign → выбранные OpenAlex/arXiv/Semantic Scholar → Literature/Market context → OpenAI structured Candidate → immutable source artifact → syntax/capability validation → causal program interpreter → public backtest → isolated hidden evaluator → retained result → next generation. Critic передаёт следующему поколению только публичные результаты. Novelty сохраняет лексическую схожесть и AST hash, не выдавая их за доказательство научной новизны.

Worker обрабатывает устойчивую очередь. Платный запрос получает резерв до отправки. При неопределённом ответе весь резерв остаётся занятым; автоматической повторной отправки нет. `tokens_charged` — консервативный резерв, фактическое usage успешного ответа хранится в артефакте. Потерявшая lease задача становится INTERRUPTED, а не исчезает. Повторный запуск требует новой явно созданной кампании. Синтаксически неверные программы сохраняются и передаются следующему поколению для исправления в пределах оставшегося числа попыток.

## Контракт стратегии

Функция `signal(history)` возвращает долю позиции от 0 до 1. Поддерживаются арифметика, локальные присваивания, условия, индексы/срезы и ограниченные чистые агрегаты. Оценка дополнительно требует долю не выше 0.2. Нет импортов, файлов, сети, произвольных инструментов, обучения нейросетей или исполнения библиотечного Python. Это ограниченный Python DSL, не универсальная среда исполнения.

Новый протокол `generated-research-v1` отделён от прежнего `demo-v1`. Он считает издержки, публичный OOS, хронологические отрезки, стресс стоимости и ограничивает позиции. Хронологические отрезки проверяют замороженный алгоритм. Дополнительно rolling selection выбирает вариант только по предыдущему обучающему окну, оставляет embargo и учитывает стоимость смены позиции. Для заранее адаптированных к публичным данным вариантов это исследовательская диагностика; обучение нейросетей не реализовано. DSR и CSCV/PBO — диагностические оценки с указанными предположениями; адаптивные исследования на открытых данных не превращают эти оценки в независимый допуск к капиталу.

## Данные

JSON импорт содержит `name`, `symbol`, `provenance`, `adjustment`, `point_in_time_verified` и массив `bars`: `time`, `available_at`, `close`, `volume`. Все даты имеют часовой пояс; 300–5000 баров, максимум 2 MB. Snapshot адресуется хешем и не изменяется. Docker API также сохраняет Parquet в локальном CAS volume; при чтении артефакта его хеш проверяется. PIT-флаг является утверждением оператора, не автоматической проверкой качества поставщика.

`scripts/import_market.py` скачивает Alpaca daily bars с пагинацией и отдельными `alpaca_data_key`/`alpaca_data_secret`. Исторические vendor revisions и survivorship не объявляются проверенными. Модель рынка рассчитывает версионированные trend/volatility/volume/regime признаки.

## Ouroboros и версии агентов

Адаптер использует существующий в родительском репозитории `/api/tasks`, опрос статуса и отмену. Настройте отдельный изолированный runtime через `ALPHA_OUROBOROS_URL` и `ALPHA_OUROBOROS_WORKSPACE`; не используйте окружение с финансовыми ключами или скрытыми данными. Фактическое подключение к такому runtime ещё требует проверки. Внешний runtime учитывает свои расходы отдельно.

API `/api/agents/revisions` сохраняет предложения изменения исследовательского prompt/workflow и обоснование OpenSpec. `/api/agents/benchmarks` регистрирует пару static/adaptive с одинаковыми данными, моделью, количеством попыток и бюджетом до выдачи в очередь. Promotion требует завершённого сравнения с лучшим результатом и решения оператора. Флажок в UI включает бюджетированное предложение новых инструкций через OpenAI после исследования. Предложения, отчёты сравнения и применение прошедшей версии доступны в UI. Автоматическое создание новых инструментов самим Ouroboros ещё не реализовано.

## Портфель и forward paper

`/api/campaigns/{id}/population` возвращает Pareto-диагностику и предложение распределения с корреляционными кластерами, ограничением веса и стрессами. Эти предложения не направляют ордера автоматически.

После PASS оператор может допустить сгенерированного кандидата через `/api/candidates/{id}/paper`. Необязательный Compose profile `forward` запускает Alpaca-feed → generated signal → immutable risk → внутренний paper fill → live evidence. Нужны отдельные ключи данных. Внешние ордера не отправляются. Открытая позиция переоценивается и проверяется даже без нового дневного бара; устаревшая котировка останавливает исполнение. Каждый кандидат получает отдельный тестовый счёт; консолидированный production portfolio ещё требует интеграции.

`brokers/` содержит paper-only Alpaca REST adapter и durable outbox с UNKNOWN/partial-fill reconciliation. Он протестирован на контролируемом транспорте, но ещё не подключён к внешнему брокерскому аккаунту и UI исполнения.

## Проверки и границы приёмки

Автотесты охватывают опасный AST, причинность, ошибки провайдера, потерю lease, права, маскирование секретов, двойные ордера, частичные исполнения и прежний risk engine. Browser smoke проверяет UI. `scripts/mock_autonomous.py` отдельно проверяет настоящие OpenAlex/E1, подменяя только генератор без затрат OpenAI. `scripts/reproduce_campaign.py` проверяет выгруженный bundle на том же runtime.

Полный master-ТЗ пока не принят: нужны live OpenAI/Ouroboros проверки, защищённые реальные PIT-данные, полноценное обучение ML, self-evolution tools, общий портфель и external paper integration, OIDC/TLS, внешнее audit anchoring и длительный benchmark/forward прогон.

Справочники реализации: [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs), [OpenAlex authentication](https://help.openalex.org/api/authentication/), [Alpaca historical bars](https://docs.alpaca.markets/us/reference/stockbarsingle-1), [Alpaca paper orders](https://docs.alpaca.markets/us/reference/postorder), [DSR](https://www.davidhbailey.com/dhbpapers/deflated-sharpe.pdf), [PBO](https://www.davidhbailey.com/dhbpapers/backtest-prob.pdf).
