# План завершения Ouromarket

Приоритет пересмотрен по запросу пользователя: сначала подключение **настоящего исходного Ouroboros**, затем завершение исполняемого инженерного цикла. В `ouroboros-runtime/` закреплена версия 6.114.0; `integration/` собирает отдельный сервер, проверяет служебную авторизацию и создаёт Git-workspace для каждого WorkOrder. Текущий профиль принимает только протокол: upstream API отклоняет выполнение без worker pool; это не генерация стратегий. Подробности и запуск — [integration/README.md](../../integration/README.md), OpenSpec `connect-pinned-ouroboros`.

Пересмотренная последовательность: (1) закреплённые исходники; (2) отдельный runtime с моделью, API и healthcheck; (3) отдельные Git-workspace; (4) передача замороженного WorkOrder; (5) сбор версионированных strategy/skill/subagent/harness артефактов; (6) независимая проверка и runner; (7) устойчивая очередь, бюджеты, отмена, аудит и UI; (8) измеряемое инженерное саморазвитие; (9) расширение исследований, PIT, E1, портфеля, risk и Alpaca paper. Работы ниже сохраняются; этот порядок уточняет их зависимости. Пока выполнены закрепление исходников и основа протокола/workspace; исполняющий профиль с OpenAI и gVisor остаётся открытым.

Срез: 2026-09-10, реализация `05308cef`. Основание: актуальная цель пользователя, исходный master-ТЗ, код и активные OpenSpec-изменения. Это план оставшихся работ, а не утверждение об их реализации. Изменения поведения приложения этим документом не вносятся.

Ход реализации, 2026-09-11: выполнен этап 1 (`unify-research-and-execution-modes`); добавлен фундамент этапа 2 (`isolated-artifact-runtime`) — отдельный JSON/native-tool controller, обязательный runsc для переданного кода, лимиты, отмена, очистка и quarantine. 359 Python-тестов проходят с полным строковым покрытием; реальные Docker fixtures проверяют исполнение и ограничения. Производственный gVisor здесь недоступен и корректно блокирует запуск. Этап 2 остаётся открытым: нужна приёмка целевого sandbox-хоста, устойчивые задания/аудит и подключение проверенных артефактов. Следующая программная работа — связать runner с реестром и бюджетами этапа 3 без передачи Docker socket агентам. Внешние paper/live режимы не включены. Исходный срез и план ниже сохранены для прослеживаемости.

## Цель и критерий завершения

Исследователь формулирует гипотезу и условия опровержения; Ouroboros реализует фиксированную спецификацию, создаёт и улучшает инженерные инструменты; независимая лаборатория проверяет результат; претенденты соревнуются с активными версиями; оператор допускает капитал; независимый risk engine и брокерский сервис исполняют разрешённые заявки. Результаты возвращаются исследователю и инженеру с сохранением границ полномочий.

Нужно отдельно подтвердить три результата:

1. **Программная готовность:** полный процесс работает, воспроизводится и выдерживает отказы.
2. **Эксплуатационная готовность:** реальные модель, данные и Alpaca paper подключены; сверка, наблюдение и восстановление проверены на длительном прогоне.
3. **Научная пригодность:** независимые эксперименты показывают пользу выбранных стратегий и инженерной эволюции после издержек и стоимости исследований.

298 тестов и 100% покрытия исполняемых Python-строк подтверждают только проверенный программный срез. Эти показатели не означают полного покрытия ветвей, отсутствия ошибок, инвестиционной пригодности или завершения master-ТЗ. Корректный результат системы может быть «ни одна стратегия не допущена, капитал остаётся свободным».

## Правила выполнения плана

Каждый этап оформляется отдельным OpenSpec change с proposal/design/tasks и проверяемыми сценариями. Названия будущих changes ниже предварительные: документы ещё не созданы. ResearchSpec отдельной стратегии и OpenSpec изменения платформы остаются разными сущностями.

Порядок поставки: спецификация → реализация → подходящие тесты → локальная проверка → небольшой коммит → push → зелёный CI → приёмка этапа. Документальные изменения проверяются как документы, без бессмысленного повторения всех runtime-тестов. Для защищённых границ обязательны отрицательные сценарии, для stateful-процессов — повтор, сбой и восстановление. Строковое покрытие сохраняется, но приоритет имеют свойства и инварианты, а не количество тестов.

## Этап 1. Единый процесс и явные режимы

**Работы:** закрепить один основной путь `ResearchSpec → Ouroboros → Laboratory`; убрать прямую совместную генерацию идеи и кода OpenAI из обычного production-пути, сохранив явно обозначенные fixtures/совместимость. Разделить synthetic/internal simulation, shadow на рыночных данных, внешний Alpaca paper и будущий live. Состояние стратегии не должно само определять её право на капитал. Исправить противоречащие текущему срезу подписи и исторические таблицы статуса. Добавить рабочую повторную валидацию пониженной версии, восстановление или создание нового forward-счёта по правилам, а не только выбор старой версии для отката.

**Приёмка:** старые синтетические PASS не дают внешний допуск; прямой API-вызов не обходит ResearchSpec или risk; пониженная версия не возвращается в работу по устаревшему доказательству. Миграции сохраняют журнал и старые ссылки.

**Зависимости:** нет. **OpenSpec:** `unify-research-and-execution-modes`.

## Этап 2. Изолированное исполнение инженерных артефактов

**Работы:** реализовать отдельный runner с контрактами входа/выхода, временной рабочей областью и воспроизводимым образом. Изолировать выполнение от ключей брокера, production checkout, hidden datasets, управляющей БД и Docker socket. Разделить сборку зависимостей и запуск: разрешённые зависимости фиксируются lockfile и digest; сетевой доступ выдаётся через ограниченные разрешения. Ограничить CPU, память, процессы, диск, время, размер результата и число дочерних задач. Поддержать отмену всей группы процессов, восстановление после сбоя и завершение оставшихся процессов. Граница изоляции для генерируемого native Python выбирается отдельным ADR; hardened Docker сам по себе не считается доказательством безопасности произвольного кода.

**Приёмка:** известный тестовый артефакт реально исполняется; проверки чтения секретов, доступа к control plane, выхода из разрешённых путей, разрастания процессов, сетевой утечки, превышения бюджета и зависания заканчиваются отказом и сохранённым событием. Один артефакт не меняет окружение следующего.

**Зависимости:** 1. **OpenSpec:** `isolated-artifact-runtime`.

## Этап 3. Полный инженерный цикл Ouroboros

**Работы:** подключить конкретный изолированный Ouroboros runtime к runner; расширить поставку до strategy package, skills, subagent manifests, harness, data validators, тестов, документации и зависимостей. Реализовать граф зависимостей, проверку capabilities, активацию проверенной версии инструмента и отзыв её прав. Общий model gateway должен учитывать исследователя, инженера и субагентов: резервировать бюджет до вызова, не допускать новых вызовов сверх лимита, сохранять фактическое потребление и обрабатывать поздние ответы. Сейчас лимит внешнего Ouroboros только запрашивается — это нужно заменить контролируемым механизмом. Неполная/отменённая работа не публикуется как пригодный артефакт.

Изменение экономической идеи возвращается исследователю для новой версии ResearchSpec. Созданный Ouroboros harness может помогать реализации, но не подменяет независимые критерии приёмки или E1.

**Приёмка:** по одной замороженной спецификации настоящий Ouroboros создаёт требуемый инструмент, инструмент исполняется в runner и участвует в реализации стратегии. Утверждения модели о прохождении тестов не принимаются без серверного прогона. Отмена и исчерпание общего бюджета прекращают дальнейшую работу субагентов.

**Зависимости:** 2. **OpenSpec:** `executable-ouroboros-engineering`.

## Этап 4. Проверяемое саморазвитие Ouroboros

**Работы:** превратить обратную связь лаборатории в инженерные задания: исправление воспроизводимости, производительности, качества данных, повторяющихся ошибок. Сравнивать старые и новые инструменты на одинаковых задачах, моделях и бюджетах. Добавить независимые инженерные задачи, не использованные при улучшении инструмента, и повторные прогоны. Измерять долю корректных реализаций, стоимость, время, число исправлений и регрессии. Вести lineage инструментов, выбор версии для новых заданий и откат после регрессии. Саморазвитие не даёт права менять модель экономической гипотезы, risk, оценку или разрешения.

**Приёмка:** полный воспроизводимый цикл `ошибка → новый skill/subagent/harness → независимое сравнение → принятая версия → её применение в следующем задании`. Улучшение должно проявиться на контрольных задачах; при отсутствии преимущества сохраняется прежняя версия.

**Зависимости:** 3; полноценная обратная связь расширяется после 6. **OpenSpec:** `measured-engineering-evolution`.

## Этап 5. Два исследовательских отдела и доказательства

**Работы:** выделить два workflow с собственной очередью, памятью, бюджетом и критериями результата. Отдел воспроизведения восстанавливает стратегию из публикации и отдельно фиксирует расхождения и новые варианты. Отдел новых гипотез использует рыночные наблюдения, противоречия и результаты работы стратегий. Добавить доступные полные тексты, формулы, таблицы, фрагменты-основания и проверку цитат. При недостатке информации исследователь должен зафиксировать пробел, а не незаметно выдумать правило. Знания хранить как проверяемые утверждения со связями supports/contradicts и версиями. Дедупликация должна учитывать экономический механизм и семейство стратегии, а не только сходство AST.

**Приёмка:** каждая спецификация содержит источник или явно новую гипотезу, механизм, данные, правила сигнала, ограничения и условие опровержения. Воспроизведение публикации и новый вариант имеют разную lineage. Инструкции из документов не становятся командами агенту. Заявление о новизне сопровождается областью проверенного поиска, а не абсолютным утверждением.

**Зависимости:** 1; пользуется 3 для реализации. **OpenSpec:** `research-departments-and-evidence`.

## Этап 6. Реальные PIT-данные, признаки и лаборатория

**Работы с данными:** создать подтверждаемую цепочку происхождения; хранить время события, публикации, получения и исправления. Добавить торговые календари, часовые пояса, корпоративные события, исторический состав universe и делистинги, где применимо. Хранить raw и adjusted series с версиями правил корректировки. Проверять пропуски, дубликаты, stale data и противоречия поставщика. Заменить операторский PIT-флаг проверяемым отчётом. Построить feature store с as-of выборкой и версиями; расчёты не должны использовать будущие исправления.

**Работы с лабораторией:** согласовать временную семантику сигнала, заявки и исполнения в backtest и forward. Перейти от единой ставки издержек к версионированной модели комиссий, bid/ask spread, проскальзывания, задержек, объёма и частичного исполнения. Глубина модели должна соответствовать доступным данным; дневные бары не подтверждают точность внутридневного исполнения. Расширить контракт стратегии для нескольких инструментов и, при необходимости, обучаемых моделей: fit/predict, сохранение параметров, seed, отдельное обучение в каждом fold. Предобработка обучается только на training-периоде. Выполнять реальные in-sample/OOS/walk-forward и стресс-проверки параметров, ликвидности, capacity и режимов.

**Приёмка:** подмена будущих данных не меняет прошлые решения; поздняя ревизия остаётся невидимой до её доступности; перенос стратегии между лабораторией и forward сохраняет значения сигналов на одинаковом доступном входе. Результат восстанавливается из образа, исходников, lockfile, данных, протокола и seed. Реальные PIT-данные имеют документированное происхождение и права использования.

**Зависимости:** 1–3 для расширенного runtime; поставщика и ingest можно готовить раньше. **OpenSpec:** отдельно `verified-pit-data` и `execution-aware-laboratory`.

## Этап 7. Независимая научная оценка

**Работы:** подключить реальный приватный набор, изолированный от публичной исследовательской выборки; проверить пересечения и происхождение. Заморозить протокол до эксперимента. Обеспечить применение нужных статистических проверок во всех маршрутах допуска: наличие DSR/PBO в диагностике само по себе не делает их обязательным gate. Учитывать всё семейство попыток, повторные проверки и adaptive selection. Разделить раскрываемую диагностику и закрытые результаты. Обновление скрытого периода должно быть операторской процедурой с сохранением истории; смена ID или перезапуск сервиса не обнуляют научный бюджет.

Результат E1 должен иметь проверяемую подпись/подтверждение отдельного сервиса, связанное с кодом, данными, протоколом и попыткой. Исследовательский writer не должен иметь возможность изготовить правдоподобную запись hidden PASS в общей БД и получить допуск.

**Приёмка:** стратегии с утечкой будущего и специально переобученные варианты отклоняются; повтор не меняет старый результат; подделка или перенос verdict на другой код отклоняются; лимиты запросов переживают сбои. Независимо проверяются формулы, предпосылки и калибровка ложных допусков. Положительный исход для конкретной стратегии заранее не гарантируется.

**Зависимости:** 6. **OpenSpec:** `independent-real-data-evaluation`.

## Этап 8. Shadow/paper-соревнование на новых котировках

**Работы:** подключить и проверить выбранный рыночный feed; сохранять общие снимки для сравниваемых версий. Учесть сессии, пропуски, разрывы соединения, поздние бары, повторные сообщения и остановки торгов. Сравнивать стратегии по чистой доходности, риску, просадке, стабильности и качеству исполнения на согласованном капитале/рисковом бюджете. Различать критерий «лучший претендент» и доказательство абсолютной пригодности; предусмотреть cash baseline. Калибровать длительность наблюдения и неопределённость; текущие 20 наблюдений — лабораторная политика, не универсальное доказательство преимущества. Сохранять все зарегистрированные сравнения, включая неудачные.

**Приёмка:** два претендента получают одни и те же доступные снимки; повтор и перезапуск не удваивают сделки; нельзя выбрать удачное окно задним числом. Превосходство оценивается по заранее выбранному протоколу. Претендент не получает реальные брокерские права.

**Зависимости:** 6–7; устойчивый feed может готовиться параллельно. **OpenSpec:** `market-forward-competition`.

## Этап 9. Общий портфель и распределение капитала

**Работы:** построить единый учёт денег, позиций, открытых заявок, резервов и долей стратегий. Сопоставлять временные ряды по timestamps/universe, а не только по длине. Научить allocator использовать только допущенные версии, оценку неопределённости, корреляцию, концентрацию, capacity и стоимость изменения позиций. Сравнить его с простыми базовыми распределениями. Неттировать сигналы нескольких стратегий в одном активе, сохраняя принадлежность результата и исключая повторный расход бюджета. Разрешить свободный капитал при отсутствии подходящих вариантов. Описать процедуру смены активной версии с уже открытыми позициями.

**Приёмка:** сумма свободного, занятого и зарезервированного капитала сходится; параллельные заявки не превышают лимит; две стратегии не продают одну позицию дважды. Отклонённая или пониженная версия не получает новую аллокацию. Старый расчёт диагностических весов не становится источником торговых прав.

**Зависимости:** 8, общий контракт с 10–11. **OpenSpec:** `portfolio-ledger-and-allocation`.

## Этап 10. Независимый risk service

**Работы:** вынести принятие торговых решений в сервис с отдельной идентичностью и правами. Он получает доверенные котировки, брокерский счёт, позиции и резервы, а не готовые утверждения агента о безопасности. Расширить контроль объёма/ликвидности, spread, участия в обороте, sector/factor exposure, коррелированных стратегий и стресс-сценариев. Учитывать действующие заявки и актуальность снимка при каждом разрешении. Сохранять versioned policy и контролируемый операторский процесс её изменения. Отдельно определить режим отмены заявок и управляемого сокращения риска при остановке, чтобы обычный запрет новых рисковых сделок не делал безопасный выход невозможным.

**Приёмка:** граничные, случайно сгенерированные и конфликтующие заявки не нарушают инварианты; отказ данных или сверки блокирует увеличение риска. Подмена разрешения, аккаунта, количества, инструмента, policy или снимка отклоняется. Risk продолжает мониторить позиции без новых сигналов. Сокращение риска проверяется самостоятельным ограниченным протоколом и не становится обходом лимитов.

**Зависимости:** 6, 9; проектирование совместно с 11. **OpenSpec:** `independent-portfolio-risk-service`.

## Этап 11. Внешнее исполнение через Alpaca paper

**Работы:** соединить подписанные approvals и outbox с отдельным брокерским сервисом, которому одному доступны торговые ключи. Реализовать подготовку заявки, резервирование, отправку, неопределённый ответ, частичное исполнение, отмену, истечение и полное закрытие. Сопоставлять брокерские события с нашим журналом; корректно обрабатывать повторы и изменение порядка событий. Сверять деньги, позиции и открытые заявки при старте, периодически и после сбоя. Не разрешать повторную отправку UNKNOWN без установления результата. Добавить распределение исполнения и издержек по стратегиям, восстановление после перезапуска и видимые оператору причины отказа.

**Приёмка:** реальный paper-аккаунт подтверждает отправку, исполнение, отмену и сверку. Контролируемые транспортные тесты покрывают редкие гонки и сбои, которые нельзя надёжно вызвать у брокера. Исследователь и Ouroboros не могут обратиться к брокеру. Отозванный допуск запрещает новую заявку даже при ранее выданном approval. Полного exactly-once внешнего транспорта не предполагаем: проверяем идемпотентность и восстановление.

**Зависимости:** 9–10; transport/reconciliation можно развивать раньше. **OpenSpec:** `alpaca-paper-execution-service`.

## Этап 12. Деградация, сокращение доли и безопасная замена

**Работы:** дополнить текущий контроль двух убыточных окон измерением фактического проскальзывания, комиссий, отказов, задержек, расхождения сигналов и сделок, смены распределений данных и рыночных режимов. Разделять потерю экономического эффекта, дефект реализации и неисправность данных/брокера. Привязать предупреждения к заранее выбранной политике: наблюдение, уменьшение лимита, запрет нового риска, paper, остановка, управляемое сокращение позиции. Возвращать экономические вопросы исследователю, инженерные — Ouroboros. Восстановление версии требует новой проверки; смена стратегии не меняет историю владения позициями.

**Приёмка:** сценарии потери доходности, роста издержек, пропажи данных и отказов дают разные объяснимые действия. Сокращение доли проходит через портфель и risk; от остановленной версии не остаются неконтролируемые новые заявки. Ложные срабатывания оцениваются на контрольных сценариях; простое отрицательное окно не объявляется научно доказанной потерей альфы.

**Зависимости:** 8–11; детекторы на replay готовятся раньше. **OpenSpec:** `degradation-and-controlled-replacement`.

## Этап 13. Операторский UI, аудит и эксплуатация

**Работы:** показать весь маршрут гипотезы и версии, работу двух отделов, реально используемые инструменты Ouroboros, сравнения, общий портфель, approvals, заявки и сверку. Разнести режимы simulation/paper/live, явно показывать недоступные функции и причины недопуска. Добавить понятную настройку модели, data feed и брокерского аккаунта, проверку соединений и отображение бюджета без раскрытия секретов. Реализовать служебные идентичности, минимум DB/сетевых прав, безопасную ротацию ключей, необходимые TLS/аутентификацию для целевого развёртывания. Обеспечить метрики, трассировку, оповещения, резервные копии, восстановление, миграции и runbooks. Подписывать manifests и закреплять аудит во внешнем неизменяемом хранилище: локальная hash chain не защищает от полной подмены базы администратором.

**Приёмка:** оператор проходит процесс через UI, видит причину решения и может восстановить доказательства; проверены роли и отсутствие секретов в UI/логах. Восстановление из резервной копии подтверждено практическим прогоном, как и отзыв ключей, остановка компонентов и потеря связи. Исторические образы и данные остаются доступны для replay. Нагрузочные/SLO и RPO/RTO требования задаются до испытаний.

**Зависимости:** сквозной этап; основа прав нужна уже во 2–3, брокерские экраны — после 11. **OpenSpec:** разделить на operator-console, provenance/audit и operational-readiness.

## Этап 14. Сквозная приёмка и отдельный live-допуск

**Работы:** выполнить настоящий путь от источника через OpenAI, Ouroboros, лабораторию, E1, shadow и портфель до Alpaca paper, затем длительное наблюдение и восстановление после отказов. Провести предварительно зарегистрированное сравнение фиксированного и эволюционирующего инженерного контура на одинаковых задачах, данных и бюджетах. Раздельно измерять пользу поиска стратегий, пользу инструментов Ouroboros и торговую пригодность; учитывать стоимость моделей и инфраструктуры. Paper-прогон должен охватывать достаточный объём наблюдений и заранее выбранные сценарии, а не просто завершиться через заданное число дней.

После успешной paper-приёмки создать отдельный live-профиль с самостоятельными ключами, правами, лимитами, сверкой и операторским разрешением. Проверить доступность инструментов и условия конкретного брокерского аккаунта. Задать ограничение капитала и план отката перед первой реальной заявкой. Наличие live-кода не считается разрешением на торговлю.

**Приёмка:** каждый переход и ордер объясним и воспроизводим; нет доступа агентов к capital/risk/E1; аварийная остановка и восстановление проверены; научный отчёт содержит все попытки и неопределённость, включая отрицательный результат. Реальная торговля начинается только после отдельного явного решения оператора. Если ни одна стратегия не проходит критерии, live не запускается.

**Зависимости:** 1–13. **OpenSpec:** `end-to-end-paper-acceptance`, затем отдельный `limited-live-admission`.

Первый следующий implementation PR: этап 1 и минимальный независимо проверяемый runner из этапа 2. Превращение сохранённых инженерных предложений в исполняемые инструменты — главный незавершённый элемент пользовательской идеи.

## Решения и внешние зависимости

До зависимого этапа нужно определить рабочую модель OpenAI и бюджет; способ развёртывания Ouroboros/runner; источник и права на PIT-данные; инструменты, частоту и торговые сессии первого релиза; data feed и Alpaca paper-аккаунт; условия операторского допуска, лимиты и требования эксплуатации. Секреты вводятся локально через защищённую настройку, не через чат.

Рабочая предпосылка первого сквозного релиза: продолжить текущий дневной long-only контур ETF без плеча, сначала внешний paper. Расширение universe и частоты — отдельное решение, после него пересматриваются данные, модель исполнения и тесты. Эта предпосылка не является рекомендацией покупать конкретный актив.

Поддержка всех источников из схемы, включая ResearchGate/Elicit/Hugging Face/GitHub, выполняется через разрешённые API, доступные тексты или импорт с сохранением происхождения. Недоступный источник не имитируется; автоматическое подключение каждого коммерческого сервиса не является условием работоспособности базового процесса. TradingView — возможный дополнительный интерфейс, не обязательная зависимость для выбранного маршрута исполнения через Alpaca.

Опционы, криптоактивы, short/leverage, HFT, распределённое обучение и неограниченное исполнение любых Python-пакетов не нужны для первой полной реализации описанного процесса. Их добавление требует отдельной спецификации. Точную календарную оценку можно дать после решений о runtime, данных и торговой частоте; время накопления независимых forward-наблюдений нельзя заменить количеством написанных тестов.
